## Context

См. `proposal.md` — «Why». Ниже только то, что определяет подход.

Сейчас генерация — один узел в конце графа (`src/chgk_agent/search/graph.py`):

```
parse_request → (embed_query | ensure_corpus_index) → (local_search | external_search)
  → score_external → merge_and_dedupe → score_matches → (rerank → needs_generation → generate | skip)
  → format_response
```

`generate` (`src/chgk_agent/search/nodes.py:470`) собирает промпт `_generation_prompt(query, matches)`, который при пустом списке совпадений отвечает на вопрос без подсказок, и кладёт результат в `GeneratedAnswer`. Развилка `needs_generation` пропускает узел при `generate_answer=false`; этот признак приходит из `SearchRequest`, лежит в настройках, в состоянии и в клиенте интерфейса. Ошибка GigaChat не отменяет запрос: узел возвращает `GeneratedAnswer(available=False, error=...)`.

`score_matches` уже выходит рано на пустом списке совпадений, а `apply_threshold` и `limit_matches` на пустом списке возвращают пустой список, поэтому пустая выдача безопасно проходит через ранжирование.

LangGraph выполняет граф супершагами: узлы, запущенные одним супершагом, идут конкурентно и завершают шаг все вместе, а следующий супершаг стартует только после этого. Отсюда два следствия, проверенных на установленном LangGraph 1.2.11 локальными пробными графами:
- узлы одного супершага выполняются конкурентно, длительность супершага равна максимуму, а не сумме задержек;
- join-узел (`add_edge([...], node)`) срабатывает ровно один раз, когда завершились все перечисленные источники;
- join из взаимно исключающих ветвей не срабатывает никогда: узел-источник обязан отработать, поэтому условная ветка «сгенерировать с контекстом | пропустить» перед join-узлом требовала бы узла-барьера.

Важное следствие для размещения: нода, поставленная в тот же супершаг, что и подготовка к поиску, перекрывается только с ней, а ветки поиска стартуют лишь следующим супершагом. Замер на графе с подготовкой 0.9 с, веткой поиска 0.4 с и двумя прогонами генерации по 1.5 с дал 3.4 с против 4.3 с у строго последовательной схемы «ответ → поиск → ответ»: первый прогон генерации перекрывается с подготовкой, а не складывается с ней.

## Goals / Non-Goals

**Goals:**
- Оба ответа получаются за один HTTP-запрос без удлинения критического пути: генерация без подгрузки перекрывается с подготовкой к поиску, а не складывается с ней набегом.
- По ответу API и по странице однозначно видно, какой прогон какой: без базы вопросов или с учётом базы.
- Отказ любого из двух прогонов не отменяет второй и не превращается в ошибку всего запроса.
- Генерация безусловна: в графе нет ветки, пропускающей её целиком.

**Non-Goals:**
- Оценка «какой ответ лучше» и автоматическое сравнение качества: страница показывает тексты рядом, судит человек.
- Сохранение пар ответов в базе для последующего анализа: сравнение живёт только в рамках одного ответа.
- Настройка-выключатель для сравнения на каждый запрос: сравнение — суть этой функции, отдельный флаг только увеличил бы число путей исполнения.
- Изменение поиска, ранжирования, порога и состава совпадений.

## Decisions

**Генерация без подгрузки — отдельная нода сразу после разбора запроса.**

```
parse_request ─┬→ generate_without_context ───────────────────────────────┐
               ├→ embed_query ─────────┐                                   │
               └→ ensure_corpus_index ─┴→ (local_search | external_search)  │
                        → merge_and_dedupe → score_matches → rerank         │
                        → generate_with_context ────────────────────────────┤
                                                                            └→ format_response
```

`generate_without_context` не зависит от совпадений, поэтому ставится в тот же супершаг, что и подготовительные ноды: он перекрывается с подготовкой, и её длительность не складывается набегом с первым вызовом модели. Последовательный вариант «сначала ответ без контекста, потом поиск и второй ответ» отклонён: он удлиняет ответ на полную длительность первого вызова GigaChat при том же числе обращений к модели.

Вариант «запускать вызов модели задачей в состоянии и ждать её в конце» отклонён: он дал бы тот же выигрыш, но потребовал бы удерживать `asyncio.Task` в состоянии графа, следить за востребованностью результата и гасить исключения у невостребованной задачи — лишняя механика там, где хватает штатной конкурентности супершага.

Дополнительная тонкость супершагов: `generate_without_context` нельзя поставить так, чтобы он пересекался и с поиском тоже. Он попадает либо в супершаг подготовки, либо в супершаг веток поиска, потому что супершаг ждёт все свои ноды. Оба варианта перекрывают генерацию с чем-то одним; выбран первый, он же и самый ранний.

**Решение о втором прогоне принимает сам узел, а не маршрутизация.**

`generate_with_context` получает уже отфильтрованные `matches` и при пустом списке не вызывает модель вовсе, возвращая `None` — отсутствие второго ответа. Условный переход с узлом-барьером дал бы тот же наблюдаемый результат, но добавил бы пустую ноду и лишние рёбра: join-узел ждёт все свои источники, поэтому пропускающая ветка требует посредника. Здесь ветка ровно одна, join собирает `generate_without_context` и `generate_with_context`, и этого достаточно. Развилка `has_results` становится ненужной: `score_matches` и `rerank` безопасны на пустом списке, а узел генерации сам решает, есть ли контекст.

**Развилка `needs_generation` и признак `generate_answer` удаляются.**

Ответ на вопрос нужен на каждом запросе, поэтому флаг лишь удваивал число путей исполнения. Удаляются: поле `SearchRequest.generate_answer`, настройка `search.generate_answer`, ключ состояния, разбор признака в `parse_request`, функция `needs_generation` и параметр метода `run` у графа. Клиент интерфейса перестаёт передавать поле, а `SearchRequest` с `extra="forbid"` начинает отклонять его как неизвестное поле — это осознанный разрыв контракта, заявленный в proposal.

**Два поля ответа вместо одного во всех слоях.**

`SearchOutcome` получает `answer_without_context` и `answer_with_context` вместо `answer`; тот же набор полей уходит в `SearchResponse`. `None` в поле означает «прогона не было», а `GeneratedAnswer(available=False)` — «прогон был и не удался». Это разные факты, и странице нужны оба: в первом случае второй ответ не показывается вовсе, во втором на его месте стоит «Не знаю». Вариант «одно поле со списком прогонов» отклонён: он перекладывает на клиента знание о том, какой элемент списка к какому прогону относится.

**Формат промпта различается наличием подсказок, а не другой ролью модели.**

Промпт без подсказок — это `Вопрос: …` и просьба ответить; блок «Раньше ты встречал такие похожие вопросы» появляется только во втором прогоне. Системная роль остаётся общей: различие прогонов задаётся контекстом, а не другим характером модели. Промпты собираются двумя отдельными функциями, чтобы отсутствие блока подсказок в первом прогоне было видно в коде и проверялось тестом.

**Отказ прогона не делает поиск частичным.**

Как и сейчас, ошибка генерации отражается в самом ответе (`available=False`, текст ошибки) и не выставляет `partial`: частичность описывает поиск, а не доступность модели. Оба прогона независимы, поэтому отказ одного не влияет на второй.

## Risks / Trade-offs

- [Двойная стоимость и двойная нагрузка на GigaChat] → Это цена функции: сравнение требует второго вызова. Счётчики GigaChat остаются прежними и не различают прогоны, поэтому рост обращений виден суммарно, а не по причинам.
- [Первый прогон не перекрывается с самим поиском] → Так устроены супершаги LangGraph: нода попадает либо в шаг подготовки, либо в шаг веток поиска. Компенсация — раннее размещение: генерация стартует первым же шагом после разбора запроса и потому перекрывается с самой долгой фазой холодного поиска.
- [Два конкурентных вызова модели на запрос упираются в `max_concurrency` и лимиты GigaChat] → Ограничение пула остаётся общим для провайдера; при исчерпании повторы и таймауты отработают как сегодня, а страница покажет «Не знаю» только на месте неудавшегося прогона.
- [Ответы могут совпасть, и сравнение не даст новой информации] → Ничего не показывать рядом нельзя: сам факт совпадения ответов и есть результат наблюдения.
- [Один прогон медленнее другого удерживает весь ответ] → Оба прогона находятся на критическом пути ответа, и медленнейший из них определяет время. Альтернатива — стриминг по мере готовности — отклонена: она меняет модель экрана и порядок блокировки формы, то есть выходит за рамки задачи.
- [Клиенты API ломаются о новую схему] → Разрыв заявлен в proposal как **BREAKING**; в репозитории единственный потребитель — веб-интерфейс, он обновляется в том же изменении, а README получает новый пример ответа.
- [Удаление признака генерации ломает автоматизацию, которая им пользовалась] → Поле отклоняется явной ошибкой валидации, а не игнорируется молча: клиент сразу видит, что контракт изменился.
- [Отказ генерации без подгрузки виден только по одному полю] → Страница и API показывают «Не знаю» на месте этого ответа, а второй остаётся доступным; тесты проверяют оба исхода по отдельности.

## Migration Plan

Изменение выпускается одним релизом: граф, схемы API и страница меняются согласованно, промежуточная совместимость со старым полем `answer` и с признаком `generate_answer` не поддерживается. Откат — возврат предыдущей версии сервиса: состояние хранится только в БД вопросов, а формат ответа задаётся кодом.

## Open Questions

- Нужно ли со временем сохранять пары ответов и отметку «помогло» для офлайн-оценки качества поиска. На текущие требования, подход и разбиение задач это не влияет: сравнение самодостаточно в рамках одного ответа.
