## Context

Промпт генерации сейчас живёт в `src/chgk_agent/search/nodes.py` (`GENERATION_SYSTEM_PROMPT`, `_generation_prompt`) и требует «опирайся только на приведённые вопросы и ответы», а условие `needs_generation` пропускает генерацию без совпадений. Интерфейс `src/chgk_agent/ui/app.py` рисует поверх ответа панель параметров, статусы источников и карточки совпадений. Настройка `SearchSettings.min_score` существует, но по умолчанию равна `0.0`.

Замеры на реальном корпусе (ресурсы и база проекта, топ-20):

| запрос | разброс локальных оценок | настоящее попадание |
|---|---|---|
| галстук | 0.774–0.904 | 0.904 (лок), 0.909 (внеш) |
| Тьюринг | 0.753–0.778 | 0.893 |
| Ангус Бейтмен | 0.830–0.893 | 1.000 |
| дизельный двигатель | 0.772–0.860 | нет |
| рецепт борща | 0.769–0.858 | нет |

Косинусная близость GigaChat имеет шумовой пол 0.75–0.88, зависящий от длины описания; реальные попадания начинаются с 0.89. Порог 0.6 не отсекает ничего, 0.88 начинает отсекать нужное.

## Goals / Non-Goals

**Goals:**
- Свести страницу к полю ввода, кнопке «Ответить» и области ответа.
- Гарантировать ответ на исходный вопрос X независимо от того, нашлись ли похожие вопросы.
- Сделать порог фильтром контекста генерации, а не условием наличия ответа.
- Не ломать HTTP API и набор качества поиска, которые опираются на `matches`.

**Non-Goals:**
- Изменение ранжирования, BM25, дедупликации и слияния источников.
- Изменение внешнего источника и его парсера.
- Стриминг ответа, история запросов, оценки пользователя.
- Починка найденного сбоя парсера внешнего источника (`invalid literal for int() with base 10: ''`).

## Decisions

**Промпт: ролевой вместо «опирайся только на эти данные».**
Системная инструкция становится ролью игрока ЧГК, а найденные вопросы передаются как необязательный контекст. Альтернатива — оставить старую инструкцию и дописать «если данных нет, отвечай по своим знаниям»: она сохраняла бы оговорку «не придумывай факты» и провоцировала отказы. Роль выбрана потому, что пользователю нужен ответ, а не отчёт о достаточности контекста.

**Порог по умолчанию 0.85.**
Обосновано замерами выше: колено между шумом (до 0.88) и попаданиями (от 0.89), с запасом вниз на случай коротких описаний, где пол ниже. Альтернативы: 0.6 (не отсекает ничего), 0.88+ (отсекает нужное). Значение остаётся настраиваемым через `CHGK_SEARCH__MIN_SCORE`.

**Ответ «Не знаю» вместо технического сообщения.**
Ошибка поиска, недоступность источников и сбой генерации дают одинаковый ответ «Не знаю», а `request_id` и текст ошибки уходят в журнал. Альтернатива — показывать `request_id` на странице: он противоречит решению «никаких технических элементов» и всё равно бесполезен пользователю, разбираться удобнее по журналу.

**Блокировка кнопки на стороне интерфейса.**
`ui.button(...).bind_enabled_from(...)` по длине нормализованного описания; при обходе блокировки обработчик проверяет описание повторно и возвращает «Не знаю», не обращаясь к API. Альтернатива — полагаться только на проверку в обработчике: тогда кнопка выглядела бы активной при пустом поле.

**API не меняется.**
`matches`, `sources`, `partial` и `truncated_query` остаются в ответе `/search`. Их использует `chgk-eval` и внешние клиенты, а стоимость их удаления выше пользы. UI просто не отображает эти поля. `generate_answer` остаётся параметром API, но UI всегда передаёт `true`.

**Удаление кода отображения, а не его отключение.**
`render_view`, `_render_sources`, `_render_matches`, `_render_match`, `_render_answer` и связанные ветки `SearchView` удаляются вместе с тестами. Оставлять мёртвый код «на случай возврата выдачи» не стоит: история изменений сохранит его.

**Источник значения порога для UI.**
UI не задаёт 0.85 литералом, а берёт `settings.search.min_score`, чтобы значение по умолчанию жило в одном месте и совпадало с настройкой сервиса.

## Risks / Trade-offs

- [Модель отвечает без опоры на базу и может ошибаться] → Это осознанное решение: пользователь получает ответ, а не отказ; ответственность за факты остаётся на модели.
- [Узкий зазор между шумом и сигналом] → Порог настраиваемый; замеры зафиксированы в design.md, чтобы значение не подбиралось заново.
- [Скрытие выдачи усложняет диагностику] → Диагностика остаётся в журнале и в API-ответе; `chgk-eval` продолжает работать через API.
- [Тесты, завязанные на показ совпадений и источников, станут неактуальны] → Их переписываем вместе с UI, а не помечаем пропущенными.
- [Потеря видимого признака недоступности источника] → Пользователь получает «Не знаю» вместо «частичных результатов»; эксплуатация видит причину в журнале и метриках.

## Migration Plan

Изменение не затрагивает схему данных и состояние сервиса, поэтому миграция не нужна. Развёртывание — обычная замена кода: перезапуск `chgk-serve` (автоперезагрузка выключена по умолчанию), затем проверка страницы `/ui` вручную. Откат — возврат предыдущей ревизии, так как внешних контрактов и данных изменение не трогает.
