## Context

Сейчас `tests/conftest.py` собирает движок из `Settings(_env_file=None)`, то есть из того же DSN, что и сервис, — `postgresql+asyncpg://…/chgk_agent`. Тестовые импорты идут через тот же `QuestionImporter`, что и боевой, и дедуплицируются по `text_hash` в таблице `questions`. Фикстура `tests/fixtures/telegram_export.html` содержит вопрос, который уже загружен в рабочую базу из `resources/messages.html`, поэтому импортёр переиспользует существующую строку и `embed_pending` со тестовым эмбеддером перезаписывает её вектор. `_purge` удаляет только тестовый `Source` и вопросы без вхождений, так что реальный вопрос остаётся с чужим вектором.

Ограничения: pgvector доступен только в локальном PostgreSQL, применять миграции умеет Alembic (`alembic upgrade head` читает DSN из `get_settings()`), у пользователя есть право `CREATEDB`, а тесты с маркером `integration` уже умеют пропускаться, когда база недоступна.

## Goals / Non-Goals

**Goals:**
- Изолировать интеграционные тесты от рабочей базы: ни одно чтение и ни одна запись не должны попадать в `chgk_agent`.
- Сделать `uv run pytest -q` работающим «из коробки»: тестовая база создаётся и мигрируется автоматически.
- Сохранить текущее поведение пропуска интеграционных тестов, когда PostgreSQL недоступен.
- Поймать опасную конфигурацию «тестовый DSN указывает на рабочую базу» до запуска тестов.

**Non-Goals:**
- Ускорение тестов, распараллеливание прогонов и кэширование подготовки схемы между запусками.
- Контейнеризация PostgreSQL или подъём сервера средствами тестов.
- Изменение поведения продукта и его спецификаций: правка касается только тестового окружения.
- Очистка рабочей базы от исторических данных — это разовая операция, а не часть механизма изоляции.

## Decisions

### 1. Тестовый DSN — отдельная настройка со значением по умолчанию
Добавляется `CHGK_DATABASE__TEST_DSN`; по умолчанию берётся рабочая настройка и заменяется имя базы на `<имя>_test` (`chgk_agent` → `chgk_agent_test`).

Почему: тесты должны работать без обязательных переменных окружения, а явная настройка нужна, чтобы указать другой сервер или базу. Альтернатива — обязательная переменная окружения — отклонена: она ломает привычный запуск и противоречит цели «работает из коробки». Альтернатива — жёсткое имя `chgk_agent_test` — отклонена: не даёт увести тесты на отдельный сервер.

### 2. Фикстуры строятся на тестовом DSN, а не на рабочем
`tests/conftest.py` создаёт движок и фабрику сессий из тестовой настройки; вспомогательный модуль подготовки принимает DSN явным аргументом, поэтому тесты, создающие временные базы, переиспользуют ту же логику.

Почему: изоляция должна обеспечиваться одной точкой, иначе новый тест снова возьмёт рабочий DSN и воспроизведёт инцидент. Альтернатива — правки в каждом тесте — отклонена как хрупкая.

### 3. Подготовка схемы — через Alembic, а не `create_all`
Перед первым интеграционным тестом движок подключается к административной базе (`postgres`), при необходимости создаёт тестовую базу и запускает `alembic upgrade head` с подменённым DSN, передавая его в Alembic явно.

Почему: схема должна совпадать с боевой, включая `CREATE EXTENSION vector`, HNSW-индекс и типы, поэтому источник истины — миграции. `create_all` их не воспроизводит. Альтернатива — отдельная база, которую разработчик готовит вручную, — отклонена по решению владельца: лишний шаг ломает «просто работает».

### 4. Проверка «тестовая база не равна рабочей» выполняется до тестов
Перед подготовкой сравниваются разобранные адреса: если имена баз совпадают, запуск завершается ошибкой с объяснением.

Почему: это ровно тот дефект, из-за которого данные были испорчены; проверка должна срабатывать раньше, чем первый тест что-то запишет, и раньше, чем `alembic upgrade head` наденет миграции на рабочую базу. Альтернатива — полагаться на аккуратность разработчика — уже показала себя плохо.

### 5. Одноразовые базы для проверки миграций
Тест, который проверяет размерность колонки под другую конфигурацию, создаёт базу с уникальным именем, применяет миграции с подменённым `CHGK_GIGACHAT__EMBEDDING_DIM` и удаляет базу в `finally` (`DROP DATABASE … WITH (FORCE)`).

Почему: этот тест уже сейчас создаёт базу, но делает это рядом с рабочей и ходит в неё через psql; перенос в общую логику убирает дублирование и риск задеть чужие данные.

### 6. Недоступность тестовой базы — пропуск, а не подмена
Если создать базу нельзя (нет прав, сервер недоступен), интеграционные тесты пропускаются с сообщением, как это происходит сейчас.

Почему: сохранение текущего поведения не ломает прогоны без PostgreSQL. Подменять тестовую базу рабочей нельзя ни при каких настройках — это и есть причина инцидента.

## Risks / Trade-offs

- **Подготовка схемы на каждый запуск замедляет тесты** → миграции применяются один раз за сессию (session-scoped фикстура), а не на каждый тест.
- **Фикстуры уровня теста откатывают транзакцию, но часть тестов коммитит** → в тестовой базе это безопасно: она изолирована; тесты, коммитящие данные, продолжают очищать их за собой.
- **Права `CREATEDB` есть не у всех** → предусмотрен путь с пропуском и подсказкой подготовить базу вручную; README описывает оба случая.
- **Ошибочный DSN можно задать осознанно** → срабатывает проверка совпадения с рабочей базой, и тесты останавливаются с понятным сообщением.
- **Тестовая база накапливает данные между прогонами** → тесты очищают свои источники и осиротевшие вопросы, а база в любой момент удаляется без последствий.

## Migration Plan

1. Добавить настройку тестового DSN и вспомогательный модуль подготовки базы.
2. Перевести фикстуры на тестовый DSN и убедиться, что полный прогон проходит на тестовой базе.
3. Пересчитать испорченный вектор в рабочей базе: `uv run chgk-reindex --force` (под фильтр по модели попадёт один вопрос).
4. Откат: убрать тестовую настройку и вернуть фикстуры на прежний DSN; тестовая база удаляется вручную и ни на что не влияет.
