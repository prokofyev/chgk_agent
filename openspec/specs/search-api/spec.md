# search-api Specification

## Purpose

Определяет асинхронный HTTP-интерфейс сервиса: контракты эндпоинтов поиска, запуска и мониторинга индексации, а также служебные проверки, которыми пользуются веб-интерфейс, автоматизация и системы эксплуатации.

## Requirements

### Requirement: Эндпоинт поиска
Система SHALL предоставлять асинхронный HTTP-эндпоинт поиска, принимающий описание вопроса и параметры поиска и возвращающий совпадения в структурированном виде с указанием источников, оценок похожести и статуса каждого источника, причём статус SHALL различать непустую выдачу, пустую выдачу, отвергнутый запрос и недоступность источника.

#### Scenario: Успешный запрос поиска
- **WHEN** клиент отправляет корректный JSON-запрос поиска
- **THEN** сервис отвечает кодом 200 и структурированным результатом, содержащим объединённые совпадения и статусы источников

#### Scenario: Некорректный запрос
- **WHEN** запрос не проходит валидацию схемы, например отсутствует описание вопроса или указан недопустимый порог
- **THEN** сервис отвечает кодом 422 с описанием полей, вызвавших ошибку валидации

#### Scenario: Ограничение размера входного описания
- **WHEN** описание вопроса превышает максимально допустимую длину
- **THEN** сервис отклоняет запрос с ошибкой валидации и не обращается к GigaChat или внешнему источнику

#### Scenario: Отвергнутый запрос внешнего источника
- **WHEN** внешний источник вернул страницу без блока результатов и без признака отсутствия совпадений
- **THEN** сервис отвечает кодом 200 и передаёт для этого источника статус отвергнутого запроса, а не пустой выдачи

### Requirement: Управление индексацией через API
Система SHALL предоставлять HTTP-эндпоинты для запуска операции импорта HTML-источников и для получения её состояния, включая итоговый отчёт по завершении.

#### Scenario: Запуск индексации
- **WHEN** клиент отправляет запрос на запуск импорта с перечнем источников
- **THEN** сервис принимает операцию в обработку и возвращает идентификатор операции для последующего мониторинга

#### Scenario: Получение состояния операции
- **WHEN** клиент запрашивает состояние операции импорта по её идентификатору
- **THEN** сервис возвращает текущий статус и счётчики прогресса

#### Scenario: Запрос неизвестной операции
- **WHEN** клиент запрашивает идентификатор операции, которая не существует
- **THEN** сервис отвечает кодом 404 и понятным сообщением об ошибке

### Requirement: Служебные проверки работоспособности
Система SHALL предоставлять эндпоинт жизнеспособности `GET /healthz` и эндпоинт готовности `GET /readyz`, причём проверка готовности MUST учитывать доступность базы данных и обязательных внешних зависимостей и MUST отвечать `503` с перечислением всех недоступных зависимостей.

#### Scenario: Проверка жизнеспособности
- **WHEN** сервис запущен и обслуживает запросы
- **THEN** `GET /healthz` отвечает кодом 200 без обращения к базе данных и внешним системам

#### Scenario: Проверка готовности при недоступной базе
- **WHEN** база данных недоступна
- **THEN** `GET /readyz` отвечает кодом 503 и перечисляет недоступные зависимости с причиной

#### Scenario: Проверка готовности при доступных зависимостях
- **WHEN** база данных доступна, а внешний источник отвечает статусом `ok` или `empty`
- **THEN** `GET /readyz` отвечает кодом 200

#### Scenario: Отключённая зависимость не делает сервис неготовым
- **WHEN** внешний источник отключён настройкой
- **THEN** `GET /readyz` отвечает кодом 200 и помечает эту зависимость статусом `disabled`, а не `unavailable`

### Requirement: Единообразная обработка ошибок
Система SHALL возвращать ошибки в едином структурированном формате, содержащем машиночитаемый код ошибки, человекочитаемое сообщение и идентификатор запроса для сопоставления с логами.

#### Scenario: Внутренняя ошибка сервиса
- **WHEN** при обработке запроса возникает непредвиденная ошибка
- **THEN** сервис отвечает кодом 500 в едином формате ошибки и не раскрывает внутренние детали реализации

#### Scenario: Прослеживаемость запроса
- **WHEN** клиент получает любой ответ об ошибке
- **THEN** ответ содержит идентификатор запроса, по которому операция находится в логах сервиса

### Requirement: Идентификатор запроса в ответах
Система SHALL возвращать в каждом HTTP-ответе заголовок `X-Request-ID`: значение, переданное клиентом, если оно есть, иначе сгенерированное сервисом. Это же значение MUST использоваться в логах и в конверте ошибок.

#### Scenario: Клиент передал идентификатор
- **WHEN** клиент присылает запрос с заголовком `X-Request-ID`
- **THEN** сервис возвращает в ответе то же значение и связывает с ним все записи логов по этому запросу

#### Scenario: Клиент не передал идентификатор
- **WHEN** запрос приходит без заголовка `X-Request-ID`
- **THEN** сервис генерирует идентификатор, возвращает его в ответе и пишет с ним логи

#### Scenario: Идентификатор в конверте ошибки
- **WHEN** запрос завершается ошибкой
- **THEN** заголовок ответа и поле `request_id` в теле содержат одно и то же значение
